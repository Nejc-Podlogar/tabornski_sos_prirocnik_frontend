## 2. OFFLINE FEASIBILITY

### Fully offline — no changes needed

| Feature | Reason |
|---|---|
| Morse translator | Hardcoded dictionary; pure local computation |
| Morse flashlight transmitter | `torch_light` package; no network dependency |
| Morse materials (dictionary) | Static data in `MorseCodeLanguage.morseCodeList` |
| Morse exercises — letters only | Random A–Z generation is local; conversion is local |
| Semaphore translator | Static image asset lookup; no network dependency |
| Semaphore materials | Static data |
| Orientation PDFs | Bundled assets |
| Settings | SharedPreferences; no network dependency |
| Onboarding | SharedPreferences flag; no network dependency |

---

### Cannot work fully offline — specific blockers named

**Home Screen News Post**
Cannot work offline. `PostCubit.getLatestPost()` calls `GET /posts/latest`. On failure it emits `PostFailure` — no local cache exists. The `InfoCard` on HomeView has no data to display. The `WebviewContainer` for news links also requires internet. The home screen has no other content.

**Morse Exercises — words and sentences**
Cannot work fully offline. The selector calls `MorseExerciseApiService.getSpecificExercise()` which POSTs to `/morse-exercise/get-exercise`. The backend calls OpenAI for these types. There is no local word/sentence generator in the Flutter app. There is no pre-seeded local corpus.

**Orientation Exercises**
Cannot work fully offline. `OrientationApiService.getExercise()` POSTs to `/orientation/get-exercise`. The backend queries the PostgreSQL `orientation` table for sign data, shuffles it, and returns `{ names, imageLoc, areCombinationsCorrect }`. Without a local copy of the orientation dataset and the shuffle algorithm, no exercise can be generated.

Additionally: all 230 topographic sign images are confirmed as bundled Flutter assets (Q2 answered) — image availability is not a risk. However, the `imageLoc` path format stored in the live DB is unknown (no INSERT statements exist in any migration; the only write path, `POST /orientation`, used wrong field names against NOT NULL columns and likely never successfully inserted any records). The Drift seed dataset mapping image filenames to sign names and categories must be authored manually.

## 3. BLOC TO RIVERPOD MAP

### ThemeBloc → `Notifier<ThemeMode>`

`ThemeBloc` has one event (`ToggleThemeEvent`) and loads initial state from SharedPreferences. All operations are synchronous once loaded. A `Notifier<ThemeMode>` with an `init()` call handles the async load on construction. `AsyncNotifier` is heavier than needed since the state itself is a simple enum value, not a data object.

---

### MorseTranslationBloc → `Notifier<MorseTranslationState>`

Seven state classes today: `Initial`, `Loading`, `Success`, `Failure`, `TorchStarted`, `TorchStopped`, `TorchFailure`. These encode both translation result and torch hardware state in one BLoC. A `Notifier` with a unified state record (translation result, direction, isTransmitting, isAutoRepeating, torch error flag) consolidates this. The torch operations are async side effects, not loading states, and do not need `AsyncNotifier`. Using `restartable()` transformer logic must be replicated manually in Riverpod (no built-in equivalent).

---

### SemaphoreBloc → `Notifier<SemaphoreState>`

Four state classes: `Initial`, `Loading`, `Success`, `Failure`. Translation is synchronous (local image lookup). `Notifier` is appropriate. `AsyncNotifier` is not warranted — there are no async data fetches. The `UpdateSemaphoreImage` event (appends to an image list) is a simple list mutation on state, straightforward in `Notifier.update()`.

---

### MorseExerciseBloc → `AsyncNotifier<MorseExerciseState>`

Eight state classes covering exercise lifecycle: `Initial`, `StartState`, `Loading`, `Validating`, `Validated`, `NotValidated`, `UndoCheck`, `NextE`. Exercise data arrives from an API call (async). `AsyncNotifier` handles the loading/error/data states. Transitions after load (validate, undo, next) are synchronous mutations on the loaded state object. Current state classes use mutable `List<?>` without type annotations — this must be replaced with immutable state records before Riverpod mapping is viable.

---

### OrientationExerciseBloc → `AsyncNotifier<OrientationExerciseState>`

Seven state classes mirroring `MorseExerciseBloc`: `Initial`, `StartState`, `Loading`, `Validated`, `NotValidated`, `UndoCheck`, `NextE`. Same analysis as MorseExerciseBloc applies. Exercise data from API is async. Post-load transitions are synchronous. Same mutability problem exists.

---

### PostCubit → `AsyncNotifier<Post?>`

Simplest mapping. One method (`getLatestPost()`), three non-initial states (`Loading`, `Success`, `Failure`). A `FutureProvider` would also work but lacks explicit `refresh()` control. `AsyncNotifier` with a `fetch()` method gives the same interface as the Cubit. State is nullable because there may be no post yet.

## 4. DATA COMPLEXITY

### Needs local persistence (Drift)

**`orientation` table**
All topographic sign records — `name`, `imageLoc`, `topoGroupType`. This is the master dataset for orientation exercises. Without it locally, no exercise can be generated. Must be seeded from the backend data before the backend is removed. Estimated record count: unknown (FRONTEND.md lists 3–25 images per category across 8 categories → likely 50–150 records).

**`morse_exercises` table**
The fallback corpus of pre-generated exercises for words and sentences. Currently grows over time as the backend generates them via OpenAI. A one-time export of this table is needed to seed Drift. For letters exercises, this table is not strictly necessary since generation is local — but exercise history, if tracked, would require persistence.

**`posts` table**
The latest news post displayed on the home screen. A single record is shown. If the home screen feature is retained in any form, this record needs to be cached locally on last successful fetch, or replaced with static bundled content.

---

### Purely algorithmic — no storage needed

| Data | Reason |
|---|---|
| Morse text ↔ Morse conversion | Hardcoded International Morse dictionary in `morseConverter.ts` / `MorseCodeLanguage.morseCodeList`. A–Z, 0–9, Š/Č/Ž. |
| Morse letter exercise generation | Random A–Z selection; conversion applied immediately. No persistence required at generation time. |
| Orientation exercise shuffle | The shuffle-and-50%-name-swap algorithm is stateless. Requires only the local sign dataset as input. |
| Semaphore translation | Static image list lookup. |
| Theme state | Simple toggle; SharedPreferences is sufficient. |
| Onboarding seen flag | Boolean in SharedPreferences. |

---

### Server-generated data requiring a local replacement strategy

**Morse words and sentences exercises**
Backend generates these via OpenAI (`gpt-3.5-turbo`). The prompt is Slovenian, domain-constrained (Morse, camping, scouting, nature, radio). The output is saved to `morse_exercises` PostgreSQL table. There is no Dart-side equivalent generator. Three possible replacement strategies exist (no recommendation made here — see Section 7).

**Post/news content**
Backend accepts `POST /posts` with no authentication to add news items. Without a backend write path, this content has no update mechanism unless an external source (CMS, static JSON bundle, third-party API) is introduced.

**`imageLoc` path values in orientation table**
These are string paths whose referent (server filesystem, CDN, Flutter asset path) is unknown. The values may need transformation when migrated to Drift — a server path like `/uploads/topografija/relief/r1.jpg` is meaningless in a Flutter asset context. The actual image files must be confirmed as either already bundled in `assets/images/topografija/` or still server-side only.

## 5. MIGRATION RISKS

Ordered by severity.

---

### CRITICAL — OpenAI dependency for Morse words/sentences

**What makes it hard:** The `POST /morse-exercise/get-exercise` endpoint calls OpenAI API with a Slovenian prompt. There is no Dart equivalent. A direct API key embedded in the Flutter app is a security risk and may violate App Store/Play Store policies. A static pre-seeded corpus is finite and will feel repetitive. The existing `morse_exercises` DB table is the fallback, but its current size and content variety are unknown.

**What could go wrong:** If the corpus is small or repetitive, the words/sentences exercise mode becomes low value. If an AI alternative is embedded client-side, key exposure is a hard security problem. If this feature is silently downgraded without communicating it, the app diverges from what the thesis describes as built.

---

### HIGH — Orientation DB seed data is absent; enum values are corrupt

**What makes it hard:** All 230 topographic sign images are confirmed as bundled Flutter assets (Q2 answered). The images are not a risk. The data risk is different and worse than originally assessed:

1. **No INSERT statements exist anywhere** in the backend codebase. No migration seeds data. No fixture files exist. The `orientation` table was created empty.
2. **The only write path is broken.** `POST /orientation` controller uses field names `type`, `value`, `translatedValue`, `length` — none of which exist on the `Orientation` entity (`name`, `imageLoc`, `topoGroupType`). With `NOT NULL` on all entity columns, every insert via this endpoint would have failed at the PostgreSQL level. There may be zero valid records in the live `orientation` table.
3. **DB enum has errors.** Migration `1720292009522` created `meje_in_morska_obala` instead of `meje_in_ograje`. This was never corrected — only `morje_in_morska_obala` was added later. The value `meje_in_ograje` (which appears in the entity code and matches the Flutter asset folder) does not exist in the DB enum. The Flutter asset folder `promet_komunikacije/` has no corresponding DB enum value — only `promet` exists.
4. **`imageLoc` format is unknown.** Since no INSERT statements were found, the actual path strings stored in the live DB (if any records exist) cannot be determined from code.

**What could go wrong:** The Drift seed dataset — the entire source of truth for orientation exercises — must be authored from scratch. There is no reliable DB export to use as input. If the live DB is assumed to contain correct data and used as the seed source without auditing, corrupt enum values (`meje_in_morska_obala`) and potentially absent records will propagate into Drift. Orientation exercises will either fail to load or show incorrect category groupings.

---

### HIGH — Orientation controller/entity field mismatch

**What makes it hard:** `POST /orientation` controller uses fields `type`, `value`, `translatedValue`, `length` — none of which exist on the `orientation` entity (`name`, `imageLoc`, `topoGroupType`). The test file `OrientationController.test.ts` also uses these wrong fields. This suggests the orientation data write path may never have worked correctly, which means the production database state may differ from what the entity schema implies.

**What could go wrong:** A DB export or data dump for seeding Drift may contain unexpected or malformed records. The Drift schema may not match what was actually stored. Exercise data seeded from a corrupt source will produce incorrect exercises silently.

---

### MEDIUM — BLoC state mutability blocks Riverpod mapping

**What makes it hard:** `MorseExerciseBloc` and `OrientationExerciseBloc` state classes hold mutable `List<?>` properties with positional constructor params lacking type annotations (FRONTEND.md, section 7). Riverpod `Notifier` requires explicit, typed, immutable state objects. The migration cannot simply wrap the existing BLoC — state classes must be redesigned from scratch.

**What could go wrong:** If mutable state patterns are carried into Riverpod inadvertently, state updates may not trigger UI rebuilds. List mutations without `copyWith` or `state = state.copyWith(...)` are silent failures in Riverpod. Testing these states is harder.

---

### MEDIUM — MorseTranslationBloc state explosion

**What makes it hard:** Seven state classes conflate two unrelated concerns: translation output state and torch hardware state. A unified Riverpod state object that correctly represents all combinations (translating, torch on, torch off, torch failed, auto-repeat on/off) requires careful design. The `restartable()` transformer from `bloc_concurrency` — used for torch transmission — has no direct Riverpod equivalent. Cancellation semantics must be reimplemented.

**What could go wrong:** Torch transmission does not cancel correctly when a new request comes in, causing overlapping flash sequences. Or the migration drops auto-repeat functionality silently.

---

### MEDIUM — `state.extra` navigation coupling with exercise data

**What makes it hard:** Exercise screens (`LearningScreen`, `OrientationScreenCards`) receive all exercise data via `state.extra` cast from `Map<String, dynamic>`. The exercise data is fetched on the selector screen and passed forward. GoRouter throws if `extra` is missing. If exercise data moves to Riverpod providers, screens can read from the provider directly — but this changes when the provider is populated and how it is invalidated between sessions.

**What could go wrong:** Exercise data is still in-flight when the screen initialises (timing issue). Or stale exercise data from a previous session is shown on a fresh navigation. Or deep-linking to an exercise screen fails because the provider has no data.

---

### LOW-MEDIUM — LearningKeyboard implementation unknown

**What makes it hard:** FRONTEND.md marks `LearningKeyboard` (`lib/screens/morse_code/learning_type_widgets/learning_keyboard.dart`) as referenced but implementation not confirmed. The thesis explicitly states keyboard mode was built. However the bloc events (`MorseExerciseValidate` with `swiperDirection` nullable) suggest the keyboard path may not have been fully integrated.

**What could go wrong:** Migration carries forward a broken or incomplete keyboard exercise feature. It appears functional until a user reaches the keyboard mode, then fails silently or with unhandled null errors (`swiperDirection` nullable without null check, FRONTEND.md section 7).

---

### LOW — Two PDF viewer packages declared

**What makes it hard:** `flutter_cached_pdfview ^0.4.2` and `flutter_pdfview ^1.4.0+1` are both in `pubspec.yaml`. It is unknown which is actually used by `PDFScreen` (whose definition location is unconfirmed). Carrying both into migration adds build weight and potential platform conflicts.

**What could go wrong:** Package conflict on one platform (iOS or Android). Or one package is removed and `PDFScreen` was using it — the PDF viewer breaks silently.

---

### LOW — InteractiveTokens enum value is dead code

**What makes it hard:** `learningInteractionType` enum includes `tokens` (interactive tokens) in both backend schema and frontend. It appears in the Drift migration if the enum is ported as-is. It is shown as a UI option in designs (S9). It is described nowhere as implemented. Including it in Drift creates a value that can be selected but produces no working UI.

**What could go wrong:** User selects "Token selector" on the exercise setup screen. The app navigates to a screen that does not handle this interaction type and crashes or shows a blank state.

---

### LOW — Posts have no auth-protected write path

**What makes it hard:** `POST /posts` and `DELETE /posts/:id` require no authentication. These are presumably used by the developer to populate the home screen. Without a backend, there is no way to update the news post shown on the home screen — unless a new content mechanism is introduced.

**What could go wrong:** Home screen always shows the same bundled news item, never updated. Or the home screen post feature is quietly removed without a stated decision.

## 7. OPEN QUESTIONS

These must be decided before architecture can be designed. No recommendations made.

---

**Q1 — What replaces OpenAI for Morse words/sentences exercises?**
The backend generates words and sentences via `gpt-3.5-turbo` in Slovenian. Three directions exist: (a) pre-seed a static corpus of exercises in Drift; (b) accept that words/sentences are offline-unavailable and disable them when offline; (c) call an AI API directly from Flutter. None of these can be assumed. This decision controls whether `morse_exercises` Drift table needs seeding, and what the `MorseExerciseApiService` replacement looks like.

**Q2 — Are topographic sign images bundled in Flutter assets, or are they server-side only?**
**ANSWERED.** All 230 topographic sign images are bundled in the Flutter app under `assets/images/topografija/`. All 8 categories are fully populated — none are empty or partial. Exact counts per category:

| Flutter asset folder | Image count | File pattern |
|---|---|---|
| `geodetske_tocke/` | 3 | `gt_1.jpeg` … `gt_3.jpeg` |
| `meje_in_ograje/` | 5 | `mo_1.jpeg` … `mo_5.jpeg` |
| `morje_in_morska_obala/` | 25 | `mmo_1.jpeg` … `mmo_25.jpeg` |
| `naselja_in_objekti/` | 48 | `nio_1.jpeg` … `nio_48.jpeg` |
| `promet_komunikacije/` | 40 | `p_k_1.jpeg` … `p_k_40.jpeg` |
| `rastje_in_vrste_tal/` | 23 | `rvt_1.jpeg` … `rvt_23.jpeg` |
| `relief/` | 28 | `r_1.jpeg` … `r_28.jpeg` |
| `vodovje/` | 58 | `v_1.jpeg` … `v_58.jpeg` |
| **Total** | **230** | |

The images are server-independent. No images are missing from the Flutter asset tree.

**However, two new problems are confirmed by this investigation:**

**Problem 1 — No `imageLoc` seed data exists anywhere in the codebase.**
There are no `INSERT` statements in any migration file. No fixture files or seed scripts were found. The `orientation` table was created empty. All orientation records were expected to be populated via `POST /orientation` at runtime — but that controller uses the wrong field names (`type`, `value`, `translatedValue`, `length`) instead of the actual entity fields (`name`, `imageLoc`, `topoGroupType`). TypeORM's `Object.assign` would silently set undefined values for all entity columns. With `NOT NULL` constraints on all three entity columns, those inserts would have failed at the PostgreSQL level. The live database state is unverifiable from code alone: the actual `imageLoc` path format stored there (if any records exist) is unknown. This is now the **primary risk for orientation data migration to Drift** — there may be no valid data in the live DB to migrate.

**Problem 2 — Three enum/folder misalignments between DB schema and Flutter assets.**

| What | DB enum value (after both migrations) | Flutter asset folder | Status |
|---|---|---|---|
| Fences category | `meje_in_morska_obala` | `meje_in_ograje/` | **MISMATCH — DB value is a historical typo from migration `1720292009522`; never corrected** |
| Traffic category | `promet` | `promet_komunikacije/` | **MISMATCH — folder name longer than enum value** |
| Sea/coast category | `morje_in_morska_obala` | `morje_in_morska_obala/` | Aligned |
| Entity enum | `MEJE_IN_OGRAJE = 'meje_in_ograje'` | `meje_in_ograje/` | Aligned with Flutter, **not with DB** |

The DB enum has `meje_in_morska_obala` (a confused merge of two category names from migration `1720292009522`) and separately added `morje_in_morska_obala` in migration `1720299949596`. The value `meje_in_ograje` — which matches both the entity code and the Flutter asset folder — **does not exist in the DB enum at all**. Any record stored with `topoGroupType = 'meje_in_ograje'` would have been rejected by PostgreSQL.

**Consequence for Drift migration:** The Drift schema must use the Flutter asset folder names as the canonical source of truth, not the DB enum values. The `promet_komunikacije` and `meje_in_ograje` names are correct; the DB values `promet` and `meje_in_morska_obala` are errors. All `imageLoc` values stored in Drift must use asset-relative paths matching the folder structure above (e.g. `assets/images/topografija/geodetske_tocke/gt_1.jpeg`). A full mapping table (name → imageLoc → topoGroupType) must be authored manually or extracted from the live DB and corrected before Drift seeding.

**Q3 — What is the home screen news post strategy post-migration?**
With no backend, `POST /posts` has no write path. Options: static bundled JSON, external CMS, read-only RSS feed, or removal of the feature. The home screen currently has no content other than the news post. This is a product decision with architectural implications (do we need any network at all?).

**Q4 — Is `LearningKeyboard` complete and correct?**
The implementation is referenced but not confirmed. FRONTEND.md notes a nullable `swiperDirection` without a null check in `MorseExerciseBloc`. Before migrating, the actual implementation must be read and tested. If it is incomplete, the migration scope must include completing it — which is not just a migration task.

**Q5 — Which PDF viewer package is canonical?**
**ANSWERED.** `flutter_pdfview` is the canonical package. `PDFScreen` is defined in [lib/widgets/pdf_custom_viewer.dart](lib/widgets/pdf_custom_viewer.dart) at line 8:

```dart
import 'package:flutter_pdfview/flutter_pdfview.dart';
```

`flutter_cached_pdfview` is unused and must be dropped from `pubspec.yaml`. No open question remains here.

**Q6 — Is InteractiveTokens (token selector learning mode) in scope?**
It appears in designs (S9 — "Token selector" tile is visible and active). It exists in the DB enum and frontend. It is not described as built in the thesis. The new DESIGN.md (Stitch AI screens) does not explicitly show a token exercise screen. In-scope or not — the decision must be explicit, because either path has consequences (build it or remove all traces of it).

**Q7 — Does `SharedPreferences` stay, or does everything move to Drift?**
Theme preference, username, avatar choice, and the onboarding-seen flag are currently in SharedPreferences. These could stay there (low complexity) or move to a Drift `user_preferences` table (consistency).
